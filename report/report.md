## 3.1. py-eval-wrapper-usage (1#2)

1. Тип срабатывания : TP (True Positive) - уязвимость с высокой потенциальной опасностью
•	вызов execute_expression() действительно присутствует, а функция использует встроенный eval(), что подтверждается кодом dangerous_eval.py. 
•	F-строка меняет синтаксис добавляя скобки, но не валидирует и не экранирует пользовательский ввод.

2. Правило Semgrep
•	id: py-eval-wrapper-usage
•	message: «Вызов execute_expression использует eval внутри»
•	severity: WARNING

3. Место срабатывания (файл и номер строки): 
•	app.py
•	18┆ result = execute_expression(prepared)

4. Соответствующий фрагмент кода

```python
@app.route("/calc")
def calc():
    expr = request.args.get("expr", "1+1")
    mode = request.args.get("mode", "direct")
    if not expr:
        expr = "0"
    if mode == "wrapped":
        prepared = f"({expr})"
        result = execute_expression(prepared)
    else:
        result = execute_expression(expr)
    return str(result)
```

5. Триаж / разбор
•	что делает этот участок кода:
Получает математическое выражение из HTTP-запроса и передаёт его на вычисление через execute_expression().
•	откуда туда попадают данные:
Из пользовательского параметра expr в URL (request.args.get("expr")).
•	что здесь потенциально небезопасного:
Пользовательский ввод передаётся в функцию, которая внутри вызывает eval().
•	почему правило Semgrep срабатывает именно здесь:
Обнаружен вызов execute_expression(...), который указан в шаблоне правила.
•	есть ли реальная уязвимость в данном проекте:
Да, поскольку данные пользователя без валидации доходят до eval() через execute_expression().
•	какой риск была бы аналогичная конструкция в реальном приложении:
Возможно выполнение произвольного Python-кода (Remote Code Execution).
•	как исправить код:
Полностью отказаться от eval() и использовать безопасный парсер арифметических выражений.

6. Как можно улучшить правило Semgrep
•	использовать taint-анализ и отслеживать путь данных от request.args, request.form, JSON и других пользовательских источников до execute_expression();
•	добавить проверку, что импортируется именно уязвимая функция из dangerous_eval.py;
•	исключить случаи с безопасными значениями, когда в execute_expression() передаются константы: execute_expression("2+2")
•	повысить severity до ERROR только при достижении eval() данными пользователя;
•	добавить сообщение с указанием, что внутри находится вызов eval(), способный привести к RCE.

## 3.3. py-command-wrapper-usage (1#1)

1. Тип срабатывания : TP (True Positive)
•	обнаружен реальный вызов run_command_template(command), а функция run_command_template() в проекте вызывает os.system() для выполнения системной команды.

2. Правило Semgrep
•	id: py-command-wrapper-usage
•	message: «Вызов run_command_template приводит к выполнению системной команды»
•	severity: WARNING

3. Место срабатывания (файл и номер строки): 
•	 app.py
•	 36┆ run_command_template(command)

4. Соответствующий фрагмент кода

```python
@app.route("/ping")
def ping():
    host = request.args.get("host", "127.0.0.1")
    count = request.args.get("count", "1")
    try:
        count_int = int(count)
    except ValueError:
        count_int = 1
    if count_int < 1:
        count_int = 1
    template = "ping -c {count} {host}"
    command = template.format(count=count_int, host=host)
    run_command_template(command)
    return "OK"

```

5. Триаж / разбор
•	что делает этот участок кода:
Формирует команду ping из параметров HTTP-запроса и запускает её через run_command_template().
•	откуда туда попадают данные:
Из GET-параметров host и count (request.args.get(...)).
•	что здесь потенциально небезопасного:
Пользовательское значение host включается в системную команду без экранирования и валидации.
•	почему правило Semgrep срабатывает именно здесь:
Правило ищет любой вызов run_command_template(...), который присутствует в данной строке.
•	есть ли реальная уязвимость в данном проекте:
Да, пользовательский ввод может попасть в os.system() через параметр «host» и «host» никак не валидируется («prefix» в «run_command_template» ничего не меняет). Параметр «count» здесь контролируется и в template попадает целое число. Но наличие безопасного «count» не делает всю команду безопасной.
•	какой риск была бы аналогичная конструкция в реальном приложении:
Возможна Command Injection с выполнением произвольных команд операционной системы.
•	как исправить код:
Использовать «subprocess.run()» без shell-интерпретации и строго валидировать параметр «host».

6. Как можно улучшить правило Semgrep
•	Использовать taint-анализ для отслеживания потока данных от request.args, request.form, JSON и других внешних источников к run_command_template().
•	Проверять, что вызывается именно реализация, которая внутри использует os.system().
•	Повышать severity до ERROR, если аргумент функции содержит данные пользователя.
•	Исключать случаи вызова с константными строками: run_command_template("ping -c 1 127.0.0.1")
•	Дополнительно помечать случаи, когда в команду подставляются данные через .format(), f-строки или конкатенацию строк.
•	Добавить в сообщение правила указание на риск Command Injection через os.system().


## 3.4.  py-requests-no-verify (1#1)

1. Тип срабатывания : TP (True Positive)
•	 в коде присутствует прямой вызов requests.get(..., verify=False), который полностью соответствует шаблону правила. 
•	К тому же здесь параметр «target» - недоверенный HTTP-ввод конпролируемый пользователем.
•	Функция возвращает только статус, и это несколько уменьшает непосредственный ущерб, но не убирает его полностью (не можем гарантировать что запрос не вернет cookies/session и тд) + потенциальный SSRF-риск.

2. Правило Semgrep
•	id: py-requests-no-verify
•	message: «requests.get с verify=False отключает проверку TLS-сертификата»
•	severity: WARNING

3. Место срабатывания (файл и номер строки): 
•	 app.py
•	50┆ r = requests.get(target, verify=False)

4.	Соответствующий фрагмент кода

```python
@app.route("/status")
def status():
    target = request.args.get("target", "https://example.com")
    r = requests.get(target, verify=False)
    return str(r.status_code)
```

5. Триаж / разбор
•	что делает этот участок кода:
Выполняет HTTP(S)-запрос к адресу, указанному пользователем «target», и возвращает HTTP-код ответа.
•	откуда туда попадают данные:
Из параметра «target»  HTTP-запроса (request.args.get("target")) – пользовательский ввод.
•	что здесь потенциально небезопасного:
Проверка TLS-сертификата отключена через «verify=False» и невалидируемый недоверенный пользовательский ввод.
•	почему правило Semgrep срабатывает именно здесь:
Обнаружен вызов requests.get() с явно заданным аргументом verify=False.
•	есть ли реальная уязвимость в данном проекте:
Да, поскольку приложение устанавливает HTTPS-соединение без проверки подлинности сертификата сервера и подтвержден невалидируемый недоверенный пользовательский ввод через параметр «target».
•	какой риск была бы аналогичная конструкция в реальном приложении:
Возможна атака типа Man-in-the-Middle (MITM) с подменой сервера и перехватом или изменением передаваемых данных. И этот код выглядит как потенциальный SSRF, потому что пользователь может выбирать сам URL.
•	как исправить код:
Удалить параметр «verify=False» либо использовать «verify=True» (поведение по умолчанию), валидировать параметр «target» (например, выбор из белого списка), добавить timeout.


6. Как можно улучшить правило Semgrep
•	добавить аналогичные проверки для requests.post(), put(), patch(), delete(), request();
•	использовать pattern-either для покрытия всех HTTP-методов библиотеки requests;
•	отслеживать случаи, когда значение передается через переменную:
insecure = False
requests.get(url, verify=insecure)
•	повысить severity до ERROR, если URL формируется из пользовательского ввода;
•	добавить taint-анализ для выявления комбинации "пользовательский URL + verify=False";
•	отдельно выявлять глобальное отключение предупреждений:
requests.packages.urllib3.disable_warnings()
поскольку это часто сопровождает использование verify=False.


## 3.5. py-os-system (1#2)

1. Тип срабатывания : TP (True Positive)
•	 в коде присутствует прямой вызов os.system(full), который полностью соответствует шаблону правила os.system(...) и параметр «command» приходит на вход функции и потенциально может содержать пользовательский ввод, который не валидируется.
•	Важно, prefix = "" это не валидация и не экранирование, то есть здесь ограничения нет.

2. Правило Semgrep
•	id: py-os-system
•	message: «Вызов os.system потенциально опасен (команда оболочки)»
•	severity: WARNING

3. Место срабатывания (файл и номер строки): 
•	command_utils.py
•	7┆ os.system(full)

4. Соответствующий фрагмент кода

```python
def run_command_template(command):
    prefix = ""
    full = prefix + command
    os.system(full)
```

5. Триаж / разбор
•	что делает этот участок кода:
Формирует строку команды и передаёт её на выполнение операционной системе через оболочку. 
•	откуда туда попадают данные:
Из аргумента функции command, передаваемого вызывающим кодом. 
•	что здесь потенциально небезопасного:
Выполняется произвольная командная строка через os.system().
•	почему правило Semgrep срабатывает именно здесь:
В коде обнаружен вызов os.system(full), соответствующий шаблону правила. 
•	есть ли реальная уязвимость в данном проекте:
Потенциально да, поскольку функция предназначена для выполнения переданной команды без каких-либо ограничений. Параметр «command» приходит на вход функции, может содержать пользовательский ввод и не валидируется
•	какой риск была бы аналогичная конструкция в реальном приложении:
Возможна Command Injection с выполнением произвольных системных команд.
•	как исправить код:
Использовать subprocess.run() без оболочки и с жёстко заданным списком разрешённых команд.

6.	Как можно улучшить правило Semgrep
Недостаток правила: оно не учитывает происхождение данных и одинаково помечает как опасные, так и безопасные вызовы.
•	использовать taint-анализ для отслеживания пользовательского ввода до os.system();
•	повысить severity до ERROR, если аргумент зависит от внешних данных;
•	дополнительно выявлять конкатенацию команд:
cmd = user_input + " --flag"
os.system(cmd)
•	добавить проверки аналогичных опасных вызовов:
subprocess.Popen(..., shell=True)
subprocess.run(..., shell=True)
os.popen(...)
•	различать вызовы с константной строкой и динамически формируемой командой для уменьшения количества малозначимых срабатываний;
•	расширить сообщение правила указанием риска Command Injection и рекомендации использовать subprocess.run(..., shell=False).


## 3.6.  py-os-system (2#2)

1. Тип срабатывания : FP (False Positive) 
•	 в коде присутствует прямой вызов os.system(command), который соответствует шаблону правила os.system(...), однако команда формируется внутри функции из жёстко заданных констант

2. Правило Semgrep
•	id: py-os-system
•	message: «Вызов os.system потенциально опасен (команда оболочки)»
•	severity: WARNING

3. Место срабатывания (файл и номер строки): 
•	 command_utils.py
•	14┆ os.system(command)

4. Соответствующий фрагмент кода

```python
def run_maintenance_ping():
    base = "ping -c 1"
    target = "127.0.0.1"
    command = f"{base} {target}"
    os.system(command)
```

5. Триаж / разбор
•	что делает этот участок кода:
Формирует команду ping для локального адреса и выполняет её через оболочку ОС. 
•	откуда туда попадают данные:
В данном примере используются только жёстко заданные константы внутри функции. 
•	что здесь потенциально небезопасного:
Используется os.system(), который запускает команду через shell, но опасности нет, так как на входе команды одни константы. 
•	почему правило Semgrep срабатывает именно здесь:
Правило обнаружило вызов os.system(command), соответствующий шаблону os.system(...).
•	есть ли реальная уязвимость в данном проекте:
Нет, в данном фрагменте команда полностью состоит из констант и не содержит пользовательского ввода. 
•	какой риск была бы аналогичная конструкция в реальном приложении:
Если бы часть команды формировалась из внешних данных, была бы возможна Command Injection. Но в данном случае уязвимость отсутствует.
•	как исправить код:
Несмотря на безопасность в данном конкретном случае, лучше заменить «os.system()» на «subprocess.run(["ping", "-c", "1", "127.0.0.1"])».

6. Как можно улучшить правило Semgrep
Недостаток правила: оно не учитывает происхождение данных и одинаково помечает как опасные, так и безопасные вызовы.
•	использовать taint-анализ и отслеживать попадание пользовательского ввода в аргумент os.system();
•	понижать приоритет или не срабатывать для константных команд;
•	различать случаи:
os.system("ping -c 1 127.0.0.1")      # низкий риск
os.system(user_command)               # (!) высокий риск
•	добавить отдельное правило для обнаружения конкатенации строк и f-string при формировании команд;
•	расширить покрытие на:
subprocess.run(..., shell=True)
subprocess.Popen(..., shell=True)
os.popen(...)
•	выдавать более точное сообщение


## 3.7. py-yaml-load (1#1)

1. Тип срабатывания : TP (True Positive)
•	 правило ищет вызовы yaml.load(...), и такой вызов действительно присутствует в коде.
•	«raw» не является доверенным значением
•	«DEFAULT_CONFIG» не делает функцию безопасной

2. Правило Semgrep
•	id: py-yaml-load
•	message: "yaml.load без безопасного Loader может быть небезопасен"
•	severity: WARNING

3. Место срабатывания (файл и номер строки): 
•	 config_utils.py
•	15┆ data = yaml.load(text)

4. Соответствующий фрагмент кода

```python
def load_yaml_config(raw):
    if raw is None or raw.strip() == "":
        text = DEFAULT_CONFIG
    else:
        text = raw
    data = yaml.load(text)
    return data

```

5. Триаж / разбор
•	что делает этот участок кода:
Загружает и разбирает YAML-конфигурацию из строки.
•	откуда туда попадают данные:
Из параметра функции raw либо из константы DEFAULT_CONFIG.
•	что здесь потенциально небезопасного:
Используется yaml.load() без явного безопасного Loader.
Злоумышленник может передать любой непустой yaml: «/config?config=<malicious YAML>»
•	почему правило Semgrep срабатывает именно здесь:
Правило ищет шаблон yaml.load(...), который присутствует в коде.
•	есть ли реальная уязвимость в данном проекте:
Потенциально да, если в raw может попасть недоверенный YAML от пользователя или внешнего источника.
•	какой риск была бы аналогичная конструкция в реальном приложении:
Возможна десериализация небезопасных объектов и, в зависимости от версии и настройки библиотеки, выполнение произвольного кода.
•	как исправить код:
Заменить yaml.load(text) на yaml.safe_load(text) либо использовать безопасный Loader явно.

6. Как можно улучшить правило Semgrep
•	Добавить исключение для безопасных вариантов:
yaml.load(text, Loader=yaml.SafeLoader)

## 3.8. py-eval-usage (1#2)

1. Тип срабатывания : TP (True Positive)	 - Критическая опасность
•	 в коде присутствует прямой вызов eval(stripped), который полностью соответствует шаблону правила eval(...) 
•	Важно откуда приходит «expr», а из файла «app.py» функции «calc()» видно что приходит из пользовательского ввода как HTTP-параметр, то есть это недоверенный ввод.

•	id: py-eval-usage

•	 dangerous_eval.py

4. Соответствующий фрагмент кода

```python
def execute_expression(expr):
    text = str(expr)
    stripped = text.strip()
    result = eval(stripped)
    return result
```

5. Триаж / разбор
•	что делает этот участок кода:
Преобразует входное значение в строку и вычисляет её как Python-выражение через eval()
•	откуда туда попадают данные:
Из аргумента функции «expr», передаваемого вызывающим кодом, которое приходит из функции «calc()» файла «app.py»  как HTTP-параметр пользовательский ввод.
•	что здесь потенциально небезопасного:
eval() выполняет переданную строку как Python-код. 
•	почему правило Semgrep срабатывает именно здесь:
Правило обнаружило прямой вызов eval(stripped). 
•	есть ли реальная уязвимость в данном проекте:
Да, поскольку функция предназначена для выполнения произвольного выражения и может получить недоверенные данные из вызывающего кода. 
•	какой риск была бы аналогичная конструкция в реальном приложении:
Возможен Remote Code Execution (RCE) с выполнением произвольного Python-кода на сервере.
•	как исправить код:
Исключить использование eval() и заменить его безопасным парсером или строго ограниченной бизнес-логикой вычислений.

•	отдельно выделять случаи, когда аргумент eval() зависит от request.args, request.form, input(), JSON и других внешних источников;
•	повысить приоритет для вызовов, достижимых из веб-маршрутов Flask/FastAPI/Django;
•	дополнительно выявлять опасные аналоги:
exec(...)
compile(...)
•	добавлять в сообщение информацию о риске RCE;
•	снижать количество малополезных срабатываний для константных выражений:
eval(user_input)
•	и повышать приоритет для динамически формируемых строк:
eval("2+2")
